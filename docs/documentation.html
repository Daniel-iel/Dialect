    Dialect

    Um framework .NET que produz SQL correto para SQL Server, PostgreSQL e MySQL a partir de uma única definição de query — via API fluente ou tradução direta de SQL existente.

    O resultado de ambos os caminhos é o mesmo formato: um CompiledQuery com Sql e Parameters, pronto para ser executado com Dapper. Dialect nunca executa comandos contra o banco — essa responsabilidade fica inteiramente com o consumidor.

    FluentBuilder

    Monte a query programaticamente em C#, com IntelliSense e checagem em tempo de compilação.

    Tradução direta

    Já tem o SQL escrito? Traduza para outro dialeto sem reescrever nada — sem depender do pattern builder.

    Princípio central

    Nem o FluentBuilder nem a tradução geram SQL diretamente. Ambos preenchem a mesma árvore de objetos (AST). Só no momento de Compile() ou Translate() um renderer específico do dialeto de destino produz o CompiledQuery final.

    Fora de escopo

    Para deixar claro onde a responsabilidade do framework termina:

    • Execução de comandos, conexão, transação, retry e pooling — fica a cargo do Dapper.
    • Mapeamento de resultado para objetos — responsabilidade do Query<T> do Dapper.
    • ORM completo (change tracking, lazy loading, unit of work).
    • Suporte a Oracle ou outros bancos além dos três iniciais — a arquitetura permite adicionar depois, mas não é v1.
    • Geração de código C# fora do fluxo da CLI de conversão de projeto (veja CLI de conversão).

    Arquitetura em camadas

    O núcleo do framework é uma árvore de objetos (AST) que representa a intenção da query, independente de qualquer banco. Um renderer específico de cada dialeto é o único responsável por transformar essa árvore em texto SQL.

    fluxo
    SqlBuilder (API fluente)          Tradução (SQL de origem)
        │                                  │

                        ▼

    Regras que sustentam essa camada:

    • O core nunca conhece bancos específicos — só conceitos abstratos como SqlFunction e SqlFeature.
    • Toda a AST é imutável após .Build() — coleções expostas usam ImmutableArray<T>.
    • O SqlBuilder é thread-confined: objeto de uso local, nunca compartilhado entre threads antes do .Build().
    • ISqlDialect é stateless e registrado como singleton via DI.

    Extensibilidade para novos bancos

    Ainda que a v1 tenha como alvo apenas SQL Server, PostgreSQL e MySQL, o projeto é desenhado para permitir a adição de novos bancos — Oracle, SQLite, MariaDB — sem alterar o core.

    • Nenhuma classe do core pode ter lógica condicional do tipo if (provider == SqlProvider.Postgres).
    • Adicionar um banco novo é criar um pacote novo, implementando ISqlDialect e IQueryRenderer, sem tocar nos pacotes existentes.
    • ISqlDialect.Supports(SqlFeature) é o mecanismo de negociação de recursos — cresce de forma aditiva, sem quebrar dialetos já existentes.
    Dialect.Oracle (hipotético)
    Dialect.Oracle
 ├── OracleDialect : ISqlDialect
 ├── OracleQueryRenderer : IQueryRenderer
 ├── OracleRoutineRenderer : IRoutineRenderer   (aqui entra "package", específico de Oracle)

    É por isso que o campo Package em RoutineCall já existe reservado (nulo, ignorado pelos três dialetos atuais) — a AST foi pensada para um banco que ainda não existe no v1.

    Select, Join & Distinct

    Um único Join(JoinType, …) genérico sustenta todos os tipos, com métodos de conveniência por cima:

    C#
    var query = SqlBuilder
    .Select("u.Id", "u.Name", "o.Total")
    .Distinct()
    .From("Users", alias: "u")
    .LeftJoin("Orders", alias: "o", on: j => j
        .On("o.UserId", Op.Equals, "u.Id")
        .And("o.Status", Op.Equals, "Paid"))
    .InnerJoin("Departments", alias: "d", on: j => j
        .On("d.Id", Op.Equals, "u.DepartmentId"))
    .Where("u.Age", Op.GreaterThan, 18)
    .GroupBy("u.Id", "u.Name", "o.Total")
    .Having("o.Total", Op.GreaterThan, 100)
    .OrderBy("u.Name")
    .Build();

    Paginação

    A API usa nomenclatura agnóstica de banco — Take() e Skip(), no estilo LINQ — nunca Top() ou Limit(), que vazariam terminologia específica de um dialeto.

    C#

    .Select("Id", "Name")
    .From("Users")
    .OrderBy("Id")
    .Take(10)
    .Skip(20)
    .Build();

    OFFSET sem ORDER BY é validado em Compile(), com erro amigável — SQL Server e a especificação ANSI exigem ordenação para paginação com offset.

    Insert, Update, Delete

    C#
    SqlBuilder.InsertInto("Users").Values(new { Name = "João", Age = 30 }).Build();

SqlBuilder.Update("Users")
    .Set("Status", "Inactive")
    .Where("LastLogin", Op.LessThan, cutoffDate)
    .Build();

    Proteção

    DELETE/UPDATE sem WHERE são bloqueados por padrão. Use .AllowFullTableOperation() explicitamente quando for intencional.

    Escape hatch (Raw)

    Sempre parametrizado — nunca concatenação livre de valores.

    C#
    .WhereRaw("EXTRACT(YEAR FROM created_at) = {0}", 2024)
.SelectRaw("JSON_VALUE(data, '$.name') AS Name")
.OrderByRaw("CASE WHEN status = 'urgent' THEN 0 ELSE 1 END")

    Uma heurística detecta concatenação suspeita (aspas desbalanceadas) no template e lança exceção. Para casos deliberadamente fora do padrão, WhereRawUnsafe() — nomeado assim de propósito, como fricção consciente em revisão de código.

    Subqueries & Derived Tables

    Aninhamento de SELECT em cláusulas FROM (derived tables) e WHERE IN para padrões de filtro complexos e agregações hierárquicas.

    FROM Subquery — Derived Tables

    Use subqueries na cláusula FROM para criar tabelas derivadas com agregação, filtragem ou transformação de dados:

    C#
    // Subquery: agregação de pedidos por usuário
var subquery = SqlBuilder
    .Select("UserId", "COUNT(*) as OrderCount", "SUM(TotalAmount) as TotalSpent")
    .From("Orders")
    .GroupBy("UserId")
    .Build();

// Query externa: filtrar usuários com mais de 5 pedidos
var query = SqlBuilder
    .Select("UserId", "OrderCount", "TotalSpent")
    .From(subquery, "UserOrders")
    .Where("OrderCount", Op.GreaterThan, 5)
    .OrderBy("TotalSpent", false)  // DESC
    .Build()
    .Compile(SqlProvider.PostgreSQL);

    WHERE IN Subquery — Filtro por resultados de subquery

    Filtre registros cuja coluna está presente (ou ausente) nos resultados de outra query:

    C# — WHERE IN
    // Subquery: todos os IDs de usuários com status "Active"
var activeUsersSubquery = SqlBuilder
    .Select("UserId")
    .From("Users")
    .Where("Status", Op.Equals, "Active")
    .Build();

// Query: pedidos de usuários ativos
var query = SqlBuilder
    .Select("OrderId", "UserId", "OrderDate", "TotalAmount")
    .From("Orders")
    .WhereIn("UserId", activeUsersSubquery)
    .Compile(SqlProvider.SqlServer);
    C# — WHERE NOT IN
    // Subquery: produtos que apareceram em algum pedido
var orderedProductsSubquery = SqlBuilder
    .Select("ProductId")
    .From("OrderItems")
    .Build();

// Query: produtos que NUNCA foram pedidos (descontinuados?)
var query = SqlBuilder
    .Select("ProductId", "Name", "Price")
    .From("Products")
    .WhereNotIn("ProductId", orderedProductsSubquery)
    .Compile(SqlProvider.MySql);

    Compatibilidade

    Subqueries são suportadas nativamente em SQL Server, PostgreSQL e MySQL. A renderização para cada dialeto é automática — não há mudanças de código necessárias ao trocar de banco.

    Procedures & Functions

    Nenhum dos três bancos alvo tem o conceito de package (isso é exclusivo do Oracle) — o campo correspondente na AST fica reservado para uso futuro.

    C#
    var call = SqlBuilder
    .CallProcedure("CreateOrder")
    .WithParameter("UserId", userId)
    .WithParameter("Total", total)
    .WithOutParameter("NewOrderId", DbType.Int32)
    .Build();

    Como a execução é feita via Dapper, CommandType.StoredProcedure resolve nativamente a chamada e os parâmetros de saída — o framework só precisa produzir o nome da rotina e os parâmetros corretos, sem montar EXEC/CALL como texto manualmente.

    AddSqlFramework — Registrando o Dialeto

    O Dialect usa métodos específicos por banco em vez de um único método genérico. Isso reflete a arquitetura real: cada banco de dados (SQL Server, PostgreSQL, MySQL) reside em seu próprio pacote NuGet com namespace separado e configuração de cache independente.

    SQL Server

    Use AddSqlServerFramework() para registrar SQL Server como dialeto padrão.

    Program.cs — Configuração Simples
    // Padrão: 1000 entradas em cache, sem eviction
builder.Services.AddSqlServerFramework();
    Program.cs — Com Configuração de Cache
    // Customizar tamanho do cache, estratégia de eviction e TTL
builder.Services.AddSqlServerFramework(
    cacheMaxEntries: 2000,
    evictionStrategy: CacheEvictionStrategy.Oldest,  // FIFO (first-in, first-out)
    cacheTtl: TimeSpan.FromMinutes(10)  // Opcional: expiração de entradas
);

    PostgreSQL

    Configuração de Cache

    Estratégias de Eviction:

    • CacheEvictionStrategy.None — Sem eviction automática. Quando o cache atinge o limite, entradas são duplicadas antes de novas serem adicionadas.
    • CacheEvictionStrategy.Oldest — FIFO (first-in, first-out). Remove a entrada mais antiga ao atingir o limite.
    • CacheEvictionStrategy.Random — Remove uma entrada aleatória ao atingir o limite.

    TTL (Time-to-Live): Opcional. Quando definido, entradas no cache expiram após o tempo especificado. Útil para:

    • Evolução de schema (novas colunas, tipos de dados)
    • Otimização em cold-start (warm up inicial)
    • Queries temporárias ou sazonais

    Recomendações:

    • Para aplicações típicas: mantenha padrão (1000 entradas, sem eviction)
    • Para altíssima concorrência: aumente cache (2000-5000) com Oldest
    • Para schemas dinâmicos: use TTL de 5-10 minutos
    • Para read-heavy patterns: Oldest geralmente supera Random

    Deliberadamente sem appsettings.json/IOptions<T> para essa escolha — a validação é síncrona e imediata no momento do registro, antes até do builder.Build().

    AddSqlTranslation

    Diferente do provider de destino, a connection string de origem é dado sensível e variável por ambiente — aqui, appsettings.json é a fonte natural, seguindo a convenção padrão do .NET.

    Program.cs
    // appsettings.json → "ConnectionStrings": { "LegacySqlServer": "Server=...;Integrated Security=True;" }

builder.Services.AddPostgreSqlFramework();  // ou AddSqlServerFramework(), AddMySqlFramework()
builder.Services.AddSqlTranslation(builder.Configuration, connectionStringName: "LegacySqlServer");

    AddSqlTranslation depende do ISqlDialect já registrado por AddSqlServerFramework, AddPostgreSqlFramework ou AddMySqlFramework — lança erro claro no registro se nenhum deles estiver presente.

    Recursos Avançados

    Além do builder básico, o Dialect oferece funcionalidades avançadas para queries complexas, otimização e manutenção de schema.

    CTEs (Common Table Expressions)

        .Select("Id", "Name", "Email")
        .From("Users")
        .Where("IsActive", Op.Equals, true))
    .From("active_users")
    .OrderBy("Name")
    .Build();

    UPSERT (Merge INSERT/UPDATE)

    Operação atômica de inserção com tratamento de conflito — se a linha já existe, atualiza; senão, insere. Cada banco tem sintaxe própria, mas a AST é uniforme.

    C#
    var upsert = SqlBuilder
    .Upsert("Users")
    .Columns("Id", "Name", "Email", "LastLogin")
    .Values(userId, userName, userEmail, DateTime.UtcNow)
    .OnConflict("Id")  // Coluna que define unicidade
    .UpdateSet("Name", userName)
    .UpdateSet("Email", userEmail)
    .UpdateSet("LastLogin", DateTime.UtcNow)
    .Build();
    BancoSintaxe nativaSuporte
    SQL ServerMERGE INTO ... WHEN MATCHED THEN UPDATE ...✅ Completo
    PostgreSQLON CONFLICT (col) DO UPDATE SET ...✅ Completo
    MySQLON DUPLICATE KEY UPDATE ...✅ Completo
    Uso típico

    UPSERT é ideal para sincronização de dados, carga incremental (ETL) e operações idempotentes. Evita boilerplate de IF EXISTS ... ELSE ...

    CLI de conversão de projeto

    Diferente da tradução (que sempre produz SQL), esta CLI existe para quando o objetivo é converter um projeto C# existente para usar o FluentBuilder — encontrando SQL cru embutido no código e gerando o código equivalente em builder.

    Performance & concorrência

    Cache de shape de query

    A mesma forma de query, com valores diferentes, sempre produz o mesmo SQL — só o parâmetro muda. Um hash estrutural da AST (ignorando literais) evita re-renderizar a mesma forma repetidamente.

    Regras de thread-safety

    1. SqlBuilder é sempre thread-confined.
    2. Tudo que sobrevive ao .Build() é imutável.
    3. O único estado mutável compartilhado é o cache — isolado atrás de ConcurrentDictionary.

    Index Advisor

    Extrai candidatos a índice diretamente da AST já existente no Compile(), sem custo de parsing adicional. Em índices compostos, colunas de igualdade vêm antes de colunas de intervalo — mais eficiente para busca em B-tree.

    Limite honesto

    A ferramenta não conhece seletividade real de dados, volume de tabela nem índices já existentes. É um assistente, não um substituto de DBA — sugestões nunca são aplicadas automaticamente.

    Batch Operations & Bulk Processing

    Otimize operações em lote com INSERT BULK, UPDATE multiple, e DELETE batch. Ideal para ETL, sincronização de dados e operações de altíssimo volume.

    Bulk INSERT

    Insira centenas de milhares de registros com performance otimizada. Use batch para aplicar transações e validações.

    C#
    using (var connection = new SqlConnection(connectionString))
{
    connection.Open();
    using (var txn = connection.BeginTransaction())
    {
        var batchSize = 1000;  // Processar em lotes de 1000
        var inserted = 0;
        
        foreach (var batch in users.Batch(batchSize))
        {
            var insertBuilder = SqlBuilder.InsertInto("Users");
            
            foreach (var user in batch)
            {
                insertBuilder
                    .Row()
                    .Value("Name", user.Name)
                    .Value("Email", user.Email)
                    .Value("CreatedAt", DateTime.UtcNow);
            }
            
            var compiled = insertBuilder.Build().Compile();
            connection.Execute(compiled.Sql, compiled.Parameters, txn);
            inserted += batch.Count();
            
            Console.WriteLine($"Inseridos: {inserted}/{users.Count}");
        }
        
        txn.Commit();
    }
}

    Advanced Migrations & Versioning

    Versionamento de schema com estado persistido, validação e rollback seguro. Mantendo histórico de mudanças e rastreabilidade.

    Estrutura de Migration

    Migrations são versionadas por timestamp ou número sequencial. O framework rastreia estado em tabela de metadata.

    C# — Criar e aplicar Migration
    // Definir migration
public class Migration202409071000_AddUsersTable : IMigration
{
    public string Version => "202409071000";
    public string Name => "Add Users Table";
    
    public string Up()
    {
        return @"
            CREATE TABLE Users (
                Id INT PRIMARY KEY IDENTITY(1,1),
                Name NVARCHAR(100) NOT NULL,
                Email NVARCHAR(100) NOT NULL UNIQUE,
                CreatedAt DATETIME2 DEFAULT GETUTCDATE()
            )";
    }
    
    public string Down()
    {
        return "DROP TABLE Users";
    }
}

// Aplicar migration
using (var connection = new SqlConnection(connectionString))
{
    connection.Open();
    var migrator = new SchemaMigrator(connection, sqlDialect);
    
    // Aplicar apenas pending migrations
    var result = migrator.MigrateUp();
    Console.WriteLine($"Aplicadas: {result.AppliedCount} migrations");
    Console.WriteLine($"Status: {result.Status}");  // "Success", "PartialFailure", "Failure"
}

    Rollback e Versionamento

    Revert migrations em ordem reversa, mantendo estado de schema sincronizado.

    C# — Rollback
    var migrator = new SchemaMigrator(connection, sqlDialect);

// Voltar 1 step
var rollback1 = migrator.RollbackOne();
Console.WriteLine($"Rollback: {rollback1.RolledBackVersion}");

// Voltar para versão específica
var rollbackTo = migrator.RollbackTo("202409061500");
Console.WriteLine($"Rolled back to: {rollbackTo.CurrentVersion}");

// Ver histórico de aplicadas
var history = migrator.GetAppliedMigrations();
foreach (var migration in history)
{
    Console.WriteLine($"{migration.Version}: {migration.Name} ({migration.AppliedAt:g})");
}
    OperaçãoDescriçãoSegurançaTempo
    MigrateUpAplicar pending migrationsAlta (validação antes)Varia com schema
    RollbackOneReverter último stepAlta (usa Down)Rápido
    RollbackTo(version)Voltar para versãoAlta (múltiplos Down)Moderado
    ValidateValidar estado atualInfo onlyRápido
    Force(version)Marcar como aplicada sem executarBaixa — manual onlyInstantâneo

    Migrations idempotentes — use IF NOT EXISTS/IF EXISTS. Testes em staging primeiro — sempre. Backup antes de rollback — produção. Versionamento imutável — não edite migrations aplicadas, crie novas.

    Security Deep Dive

    Proteção contra SQL injection, quando Raw() é seguro, boas práticas de binding, auditoria e validação.

    SQL Injection Protection via Parameterization

    O builder fluente por padrão é 100% seguro — tudo é parametrizado automaticamente.

    C# — Seguro por padrão
    // ✅ SEGURO — Parâmetro automático
var userId = "1 OR 1=1";  // Tentativa de SQL injection
var query = SqlBuilder
    .Select("*")
    .From("Users")
    .Where("Id", Op.Equals, userId)  // Parametrizado internamente
    .Build();

var compiled = query.Compile();
// SQL: SELECT * FROM Users WHERE Id = @UserId
// Parâmetro: { "@UserId": "1 OR 1=1" } — tratado como valor literal, não SQL

    Quando usar Raw() — e como fazer seguro

    Raw() e RawUnsafe() contornam parameterização. Use apenas com dados confiáveis.

    C# — Raw() Seguro vs Inseguro
    // ✅ Raw() SEGURO — Ainda usa parâmetros
var year = 2024;
var query1 = SqlBuilder
    .Select("*")
    .FromRaw("SELECT * FROM Orders WHERE YEAR(CreatedAt) = {0}", year)
    .Build();
// Template {0} é substituído por parâmetro, não concatenação

// ❌ Raw() INSEGURO — Concatenação direta (NUNCA FAÇA)
var userInput = request.GetQueryParameter("column");
var query2 = SqlBuilder
    .Select(userInput)  // ❌ INJECTION RISK
    .From("Users")
    .Build();

// ✅ Raw() com validação — ACEITO para valores fixos
var validColumns = new[] { "Id", "Name", "Email" };
var columnInput = request.GetQueryParameter("column");
if (!validColumns.Contains(columnInput))
    throw new ArgumentException("Coluna inválida");
var query3 = SqlBuilder
    .Select(columnInput)  // Agora seguro (whitelist)
    .From("Users")
    .Build();

// ✅ RawUnsafe() — Explicitamente marcado para revisor
var query4 = SqlBuilder
    .SelectRaw("JSON_VALUE(data, '$.field') AS Field")  // Safe — string fixa
    .From("Users")
    .Build();

    Input Validation & Constraints

    Valide schemas antes de compilar queries para evitar mismatches.

    C#
    // Validar schema antes de compilar
var schema = new SchemaValidator(sqlDialect);

{
    foreach (var error in schema.Errors)
        Console.WriteLine($"Schema validation error: {error}");

    Nunca concatene user input diretamente em queries. Use sempre builder com parâmetros. Se precisar de Raw, valide contra whitelist. RawUnsafe() é explicitamente tóxico em code review para alertar revisor.

    FAQ

    P: Como escolho entre SQL Server, PostgreSQL e MySQL?

    R: Todos são suportados igualmente. Escolha por infraestrutura, custo ou preferência pessoal.

    P: Posso trocar de banco de dados sem reescrever código?

    R: Sim! Use .Compile(SqlProvider.PostgreSQL) para trocar dialetos.

    P: Qual é o impacto de performance do Dialect?

    R: Minimal. Queries são compiladas uma vez e cacheadas. Overhead < 1ms por query.

    P: Funciona com Entity Framework?

    R: Dialect é uma alternativa ao EF. Use Dialect ou EF, não ambos no mesmo projeto.

    P: Posso usar Dialect com Dapper?

    R: Sim! Perfeito. Dialect gera SQL pronto para Dapper.
